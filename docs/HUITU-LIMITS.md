# 慧图馆方限制实测（2026-11-13）

真实账号实测所得，非推测。原始报文与凭据仅留在本机 `artifacts/probe/`（已 gitignore），本文已脱敏。

## 1. 读写限流是两套量级

| 路径 | 接口 | 间隔 | 结果 |
|---|---|---|---|
| 读 | `POST /Seat/Index/searchSeats` | 亚秒级串行 × 40 | 全部 200，**零限流**，单次 199–498ms |
| 读 | 同上 | **0ms 背靠背 × 60** | **60/60 通过**，3.4 rps，205–510ms，无任何限流 |
| 读 | 同上 | **6 路并发 × 15** | 62/90，出现 `HTTP 404` |
| 读 | 同上 | **8 路并发 × 12** | 93/96，3 次 404 |
| 读 | 同上 | **12 路并发 × 8** | 81/96，3 条 lane 命中 404 |
| 写 | `POST /Seat/Index/bookSeats` | 亚秒级 | #2 `请求太频繁了` → #3 `请求过于频繁，请10分钟后再试` |
| 写 | 同上 | 3s（紧接前一轮后） | #2 直接封禁 |
| 写 | 同上 | 5s | 首轮 8/8 通过；**次轮 #6 封禁** |
| 写 | 同上 | 10s | 两阶段共 12 次写入（lock/book/unlock/cancel）未被限流 |

**读路径没有速率限制，只有并发限制**：串行零间隔连打 60 次全过；一旦并发就出现 404。
判定实验：8 路并发打出 3 次 404 后**立刻串行 10 次（零间隔）→ 10/10 全部 200**，
说明 404 是瞬时并发保护，**不累积、不封禁、无需等待**。

- 写入额度是**累积桶**，不是单次间隔判定：5s 首轮通过只是窗口未耗尽。
- 写入封禁**只影响写入**：封禁期内读接口连打 3 次仍全部 200。
- 写入封禁时长与服务端文案一致：等满 600s 后首个写请求即通过（两次封禁均复现）。
- 桶容量与窗口未测出确切值。已确认：**亚秒级 / 3s / 5s 都会触发封禁**；10s 在连续 12 次写入中通过。10s 之后的一次封禁发生在紧随其后的 5s 测试中，不能归因于 10s。
- **10s 不是绝对安全线**：§2.1 实测中，桶已被前一轮消耗后，10s 节拍的第 2 次写入即封号。10s 只在桶有余量时安全，故命中 ban 必须立即停手。

### 1.1 `HTTP 404` 的真实身份（修正 issue #4 的归因）

404 **不是网关错误页**，而是应用自己的 JSON 业务响应：

```
HTTP/1.1 404   server: nginx   content-type: application/json; charset=utf-8
{"CODE":"NotFound","ui_type":"com.Message"}
```

它经 `HduError::Http(404)` → `"HTTP 404"` → `"房间或座位查询失败: HTTP 404"`，
与 issue #4 审计中的三条记录完全一致。**成因是并发保护，而非"馆方网关过载"**。
本工具串行执行、并发度为 1，因此自身不会触发；20:00 出现的 404 来自大量客户端同时抢座时服务端的整体并发保护。
推论：读路径遇 404 应**尽快重试**（下一拍即可），退避等待反而是错的——旧指数退避把间隔拉到 65s，正好错过恢复窗口。

### 1.2 404 保护按端点生效（实测）

并发压 `searchSeats` POST 期间同步采样其他读端点：

| 端点 | 结果 |
|---|---|
| `searchSeats` **POST** | 112 ok / **8 次 404** |
| `baseInfo` | 6/6 全 200 |
| `myBookingList` | 6/6 全 200 |
| `searchSeats` **GET** | 6/6 全 200 |

**探活必须用 `searchSeats` POST 本身**：拿 `baseInfo` 或同路径 GET 探到 200 是假信号，选座通路可能仍在 404。

### 1.3 20:00 的实际表现（用户实况 + 实测互证）

用户实况：20:00 会持续 404 约 **1–2 分钟**才恢复。这与 §1 的"瞬时恢复"不矛盾——
404 是并发保护，实测中停掉并发即刻恢复；20:00 全校客户端持续猛打，压力不退，故持续 1–2 分钟。
**同一机制、两种表现**。推论：404 期间不该退避（它不是封禁），但也不该高频空打。

写入侧在**非高峰时段**不存在"404 挡回"：5 路并发 `bookSeats` 实测得到 15 次 200 + **直接封禁**，零个 404。
写入限流优先级高于并发保护，撞上去就是封号 10 分钟。

**但 20:00 高峰例外**：11-11 / 11-12 / 11-13 连续三晚首轮 `bookSeats` 都收到 `HTTP 404`
（审计中表现为无前缀的 `HTTP 404` + 带 `seatNum`，区别于座位图失败的 `房间或座位查询失败: HTTP 404`）。
说明高峰期的并发保护同样覆盖写端点。这类 404 与读侧同性质：不累积、下一拍可重试。

## 2. 座位可用性由 `POI.state` 决定

`seatMap.POIs[].state`（字符串或数字）：

| state | 提交结果 |
|---|---|
| `0` | `CODE=ok` / `result=success`，预约成功 |
| `1` / `3` | `ParamError`：`选择的座位无法预约，可能座位不可用或已经被其他人锁定或占用` |

某时刻 +1 日 08:00 全馆分布：`{0: 1513, 1: 380, 3: 1}`。

### 2.1 失败提交是否消耗写入额度（决定性实验）

质疑："先用座位图筛掉已占座位以节省提交次数"是否成立？关键在于**被拒的提交算不算写入**。
用 `quota` 探针实测：连续对 state≠0 的座位提交，再紧接着提交一个空闲座位。

| 节拍 | 已占座位提交 | 结果 |
|---|---|---|
| 10s | 4 次全部 `ParamError`，随后空闲座位提交 | `result=success` → 未耗尽额度 |
| 亚秒级 | #1 `ParamError` → **#2 `请求太频繁了`** | 第 2 次即被限流 |
| 10s（紧接上一轮后） | #1 `ParamError` → **#2 `请求过于频繁，请10分钟后再试`** | 第 2 次即封号 |

**结论：失败提交同样计入写入额度。** 亚秒级下第 1 次业务失败之后第 2 次就被限流；
累积桶已被前一轮消耗时，10s 节拍下第 2 次直接封号。
10s 首轮 4 次失败后仍能成功，只是窗口尚未耗尽——与 §1 中"5s 首轮 8 次通过"同一机制。

所以按 state 预筛**是有意义的**：每次被拒的提交都在消耗与成功提交同一份稀缺额度，
而 20:00 全馆约 20% 座位 state≠0（385/1894）。不预筛就会把额度花在必然失败的座位上。

补充：这也修正了"10s 绝对安全"的乐观解读——10s 只在桶有余量时安全，
故命中 ban 必须立即停手（§6），且预锁逐成员锁座也要走同一节拍（§8）。

## 3. 预锁不是预约前提

- 对**空闲座位**（state=0）调 `lockSeats`：`CODE=ok`、`DATA.time>0`，但 **`DATA.result=fail`**；紧接着 `bookSeats` 直接成功。
- 对已占座位调 `lockSeats`：同样 `CODE=ok` + `time>0` + `result=fail`。
- 结论：`lockSeats` 只能当**座位提示**，`result=fail` **不代表不能预约**。

### 3.1 `result=fail` 不得导致 seatId 被丢弃（2026-11-13 实战教训）

既然空闲座位就是回 `fail`，那么"要求 `result=success` 才保留 seatId"等价于**永远不保留**。
v2.1.4 首晚实战即因此失效：

```
19:59:01  预锁 CODE=ok / result=fail → 判失败 → locks=0（seatId 被扔）
20:00:15  首轮提交被 404 挡回
20:00:19  起 12 轮座位图 404/超时 → 无 seatId → 一次提交都发不出
20:02:15  座位图恢复，重新解析 seatId → 提交成功（耗时 136s，其中 86s 干等）
```

座位全程空闲（最后原样抢到即证明），19:59 拿到的 seatId 完全可用。

**正确判据**：座位空闲（`POI.state=0`，§2）**且**馆方受理了请求（`CODE=ok`）→ 保留 seatId。
`CODE != ok`（如限流 `CODE=1`）才代表请求没被受理，此时不保留。
`DATA.result` 只写进日志与审计的 `held` 字段，**不参与决策**。

| 函数 | 含义 | 用途 |
|---|---|---|
| `lock_accepted` | `CODE=ok` | 决定是否保留 seatId |
| `lock_effective` | `CODE=ok` 且 `result=success` | 仅日志展示（`BookingLock.locked`） |

测试夹具的 `lock_result` 默认值必须是 "fail"（与真馆方一致）。
此前默认 "success"，导致所有"预锁被消费"的用例都跑在现实中不存在的前提上，
当时 94 个测试全绿却漏掉了这个缺陷。

## 4. 提交前不强制重查座位图

预约 A → 取消 → **不做任何新 `searchSeats`** → 直接提交座位 B：`result=success`。
旧注释所称"服务端校验查询→提交流程"在实测中未出现。座位图查询仅用于解析 seatId 与筛 state，每轮一次即可。

### 4.1 这条契约与 20:00 持续 404 的关系（预锁的核心价值）

20:00 座位图可能持续 404 达 1–2 分钟（§1.3）。此时：

- **有预锁**：`seatId` 在 19:59:00 就已拿到，404 期间照样能提交。
  正是 §4 这条"免查询也能提交"的契约让预锁在拥堵时仍然有用。
- **无预锁**：`seatId` 只能从座位图解析，404 期间无候选可试，只能等恢复。

由此得出一条必须遵守的实现约束：**404 期间绝不能丢掉预锁**。
丢锁后 seatId 无处可取，整个窗口会退化成只读不提交。

已修复的两处相关缺陷（均由模拟 20:00 场景的测试复现）：

| 缺陷 | 后果 | 修法 |
|---|---|---|
| 任何非 terminal 失败都丢锁 | 首次提交遇"未到预约时间"即丢锁，第二轮起 `book_calls` 停在 1，整窗口不再提交 | 只有 `is_seat_unavailable_message` 为真才丢锁 |
| 提交结果覆盖 `seat_query_busy` | 有预锁时本轮会提交，busy 标记被覆盖 → 写入槽冻结完全失效 | 独立变量记录，所有出口统一带上 |

## 5. 其他已确认契约

- `GET /User/Center/baseInfo` **不能带 `LAB_JSON=1`**：带了返回 UI 页 `com.BackRefreshPage`，不带才返回 `CODE=ok` + `DATA.is_login`。
- 业务失败文案取 `DATA.msg`，其次顶层 `MESSAGE`；预约成功需 `CODE=ok` **且** `DATA.result=success`。
- **取消预约成功时 `DATA` 内没有 `result` 字段**：实测原始报文为 `CODE=ok`、`MESSAGE=取消预约成功`，`DATA` 只含用户信息（`is_login`/`uid`/`uname` 等）。旧 `assert_action_success` 强求 `result=success`，会把成功取消误判为失败，并连带跳过 `scheduler.forget()`。现改为：`result` 存在时必须为 `success`，缺失时以 `CODE=ok` 为准；限流 `CODE=1` 仍被挡住。
  - 交叉验证：取消 A 后对同一时段提交 B 成功（未报"已有预约"），证明取消确实生效。
- 同时段重复提交：`ParamError` / `已有预约，请勿重复预约！`。
- 超出可约日期：`ParamError` / `超出可预约座位时间范围`。
- `range`：`minBeginTime=7`、`maxEndTime=22`、`min_duration=1`、`max_duration=15`、`max_num=4`，可约日期由 `advance_date`/`max_date` 界定。
- 签到窗口：`limitSignAgo=1800`、`limitSignBack=1800`（秒）。

### 6.1 为什么读不设节流，轮询统一 300ms

旧实现对任何失败一视同仁地指数退避，404 也被拉长到 65s——而 404 其实下一发就能成功。
这是 issue #4 错过窗口的直接机制。

**读路径的秒级节拍已删除**：实测零间隔背靠背 60 次全部 200（3.4 rps），
任何秒级间隔都找不到实测依据，纯粹是白等。现在读请求之间没有任何人为等待，
`read_slot` / `read_interval_ms` / `paced()` 全部移除。

剩下的等待只有两处，各有实测依据：

| 位置 | 值 | 依据 |
|---|---|---|
| 轮询睡眠（任何失败后） | `POLL_MS = 300` | 404 不累积、瞬时恢复；300ms 只为避免忙循环 |
| 写请求节拍 `paced_write` | 10s | 亚秒级/3s/5s 均触发封禁，10s 连续 12 次通过 |
| 写 ban（`请求过于频繁`） | 停手等 600s | 封禁期内提交无效 |

404 与业务失败现在走**同一个** 300ms，不再分快慢两档——既然读无速率限制，
分档就没有意义。300ms 覆盖 20:00 拥堵 2 分钟约 400 次探测，恢复检测最多晚 300ms。

### 6.2 轮询的结束条件

`run_burst` 每轮结束后按顺序判定，命中任一即返回：

| 条件 | 说明 |
|---|---|
| 有成员 `blocked`（ban） | 立即停手，封禁期内提交无效 |
| `result.success` | **全部成员成功 → 立即结束，不再轮询** |
| 无可继续成员 | 每个成员非 success 即 terminal，无事可做 |
| 到 `timeout_ms`（10 分钟） | 兜底上限 |

**members 为空也算"无可继续成员"**：今日不在方案重复日期内时 `member_begin` 全部返回
`None`，重试不会有变化。旧实现把空 members 当作"还有待办"，导致整个窗口空转——
实测 2 秒内跑了 **17522 轮**（每轮一次预约列表查询）。已修复。

已成功的成员进 `finished`，后续轮次直接复用结果，不重复提交。
`unverified` 累计 3 次转终态，避免无限确认。

对应测试：`success_ends_polling_immediately`、`group_success_ends_polling_immediately`、
`no_actionable_member_ends_polling_immediately`、`terminal_failure_ends_polling_immediately`。

### 6.3 超时与拥堵统计（2026-11-13 实战修正）

**读超时必须远短于写超时。** 原实现读写共用 30s（Rust 迁移时的取值，为的是"预锁不跨 20:00"）。
但读路径正常只要 205–510ms，一个卡住的连接要占满 30s 才放弃，期间无法重试。
当晚两次读超时各耗 30.6s / 30.8s，合计约 60s，占 136s 窗口的 **44%**。

| 路径 | 超时 | 依据 |
|---|---|---|
| 读（座位图 / 预约列表 / 房间目录 / baseInfo） | `READ_TIMEOUT_SECONDS = 5` | 正常上限 510ms 的约 10 倍，留足拥堵余量 |
| 写（bookSeats / lockSeats / 签到 / 取消等） | `WRITE_TIMEOUT_SECONDS = 30` | 预锁提前量 60s 的上界依赖它；写入放弃后无从判断是否已落单 |

两个常量都在 `core::time`，由 `prelock_lead_exceeds_the_http_timeout` 与
`read_timeout_is_much_shorter_than_write_timeout` 守住关系。

**超时也算"座位图不可用"。** `seat_query_busy` 原先只认 `Http(404)`，
`RequestTimeout` 不匹配 → 上层以为拥堵退了 → 写出假的 `booking_seat_query_recovered`。
当晚两次 recovered（`busyMs` 34866 / 51554）都是这么来的，馆方其实一直在 404。
假恢复还会解冻写入槽，让真正恢复的瞬间连发提交。
现由 `is_seat_query_blocked` 统一判定：`Http(404)` 与 `RequestTimeout` 都算。

**`busyRounds` 按段计数。** 原实现跨段累加，当晚第二段记成 10 轮（含第一段的 3 轮），
与 `busyMs` 不符。现在每次写 recovered 后归零。

对应测试：`a_read_timeout_is_not_a_recovery`、`busy_rounds_are_counted_per_window`、
`read_requests_give_up_at_the_read_timeout`、`write_requests_keep_the_longer_timeout`。

## 7. 读写节拍的最终取值

**读路径零节流**：零间隔 60 次全过说明读路径根本不需要节流；
唯一保留的 300ms 是轮询睡眠，作用是避免 404 持续时退化成忙循环，不是限流规避。

**写路径必须 10s**：亚秒级连打第 3 次即封号 10 分钟，等于抢座窗口内自毁。故写入按实测取 10s，并保留命中封禁立即停手（封禁期内提交无效，继续打只会空耗）。这是"以实测逻辑写代码"的直接结果，而非保留旧的退避设计。

## 8. 预锁：19:59:00 逐成员各一次，失败只记日志

预锁在 **19:59:00** 触发，对启用方案的**每个成员各发一次**请求：
单方案 1 个成员 → 1 次；组合方案 N 个成员 → N 次。
每个成员一次座位图查询 + 一次 `lockSeats`，然后结束。

**每个成员只请求一次**：失败不回退、不兜底、不重试、不换备选座位，
只把该成员的失败原因记进日志，继续下一个成员。

关键约束：

- **预锁不是预约前提**（§3）：任何成员失败都不影响正式预约，
  20:00 照常按主座位 + 备选进行。
- **写入必须走节拍**：组合有 N 个成员就有 N 次 `lockSeats`，
  故锁座走 `paced_write`（实测 10s）。直连发会撞累积额度（§1，3 次即封号）。
- **不跨 20:00**：提前量 60s，写请求最坏 30s（`WRITE_TIMEOUT_SECONDS`），
  正常路径每成员约 0.5s + 写入节拍。
  这一点很关键——`booking_anchor_delay_seconds` 在时刻 ≥20:00 时返回 `+24h`，
  预锁跨过锚点会把当天预约推到**第二天**，当天完全不抢。

实现要点：

| 位置 | 行为 |
|---|---|
| `core::BOOKING_PRELOCK_LEAD_SECONDS = 60` | 提前量 60s，即 19:59:00 |
| `scheduler::prelock_once` | 到点调用一次；登录态失效只记 `booking_prelock_skipped` |
| `BookingExecutor::lock_once` | 遍历成员，每个各一次；受理成功的才存座位提示 |
| `BookingExecutor::prelock_attempt` | 单成员一次查询 + 一次锁座（走写入节拍） |
| 审计 `booking_prelock_finished` | 记 `success`/`members`/`attempted`/`locks`/`held`/`elapsedMs`/`message` |

失败原因带座位号进日志：座位查询失败、座位不在座位图中、座位已被占用、锁座失败、锁座被拒。

**`result=fail` 不算失败**（§3.1）：空闲座位就是回 fail，seatId 照常保留并被正式预约消费。
`locks` 是就绪的座位号数量，`held` 是其中真正锁住的数量（常为 0，仅供观察）。
整体 `success` 仅在"有成员被尝试且全部就绪"时为真。

对应测试：`prelock_covers_every_group_member_once`、`prelock_continues_after_one_member_fails`、
`prelock_issues_one_request_for_a_single_plan`、`prelock_failure_is_logged_without_retry`、
`prelock_skips_an_occupied_seat_without_retry`、`prelock_logs_the_ban_without_retrying`、
`lock_result_fail_still_keeps_the_seat_id`、`lock_rejected_by_code_keeps_no_seat_id`、
`real_world_prelock_survives_a_persistent_404_window`，
以及 core 的 `prelock_lead_exceeds_the_http_timeout`。
